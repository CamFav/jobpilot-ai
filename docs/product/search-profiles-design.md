# Search profiles design

## Purpose

A search profile represents one independent job-search intent for one user. A user can keep several profiles active or paused, for example “Java backend in Lyon” and “remote product roles”. This document defines the MVP design only; it does not create an application, API contract, database migration, or matching engine.

It follows the [product vision](vision.md), [backend architecture guidelines](../architecture/backend-guidelines.md), and [coding standards](../development/coding-standards.md).

## MVP scope

The MVP lets an authenticated user create, read, update, pause, reactivate, and delete their own profiles. A profile contains:

- a profile name;
- one or more target job titles;
- optional skills and keywords;
- one or more geographic locations;
- optional work modes and contract types;
- optional salary preference;
- required and preferred criteria;
- an active or paused status.

The MVP does not import offers, calculate match scores, resolve locations through a geocoding provider, interpret free-text criteria with AI, or submit applications. It stores a clear user intent that future opportunity and recommendation modules can consume.

## Domain model

### Aggregate

`SearchProfile` is the aggregate root owned by the `identityprofile` module. It owns its configuration and state transitions. It is not a persistence entity or REST payload.

| Element | Purpose |
| --- | --- |
| `SearchProfileId` | UUID generated by the application; stable identifier exposed through the API. |
| `UserId` | UUID of the owner, supplied by the authenticated identity context; never accepted as an API request field. |
| `ProfileName` | Non-blank user-facing name, normalized for uniqueness per owner. |
| `SearchProfileStatus` | `ACTIVE` or `PAUSED`. |
| `TargetJobTitle` | Non-blank title the user seeks; at least one is required. |
| `SkillKeyword` | Optional user-entered skill or keyword; normalized for de-duplication while retaining a display value. |
| `SearchLocation` | A non-blank geographic display label and an optional ISO 3166-1 alpha-2 country code. Coordinates and radius are out of scope. `REMOTE` is not a location. |
| `WorkMode` | `ONSITE`, `HYBRID`, or `REMOTE`. |
| `ContractType` | `PERMANENT`, `FIXED_TERM`, `CONTRACTOR`, `FREELANCE`, `INTERNSHIP`, `APPRENTICESHIP`, `TEMPORARY`, or `OTHER`. UI labels are localized; values remain stable API values. |
| `CompensationPreference` | Optional minimum and/or maximum amount, currency, and period (`YEAR`, `MONTH`, `DAY`, `HOUR`). It expresses preference, not an offer filter by itself. |
| `ProfileCriterion` | A non-blank description plus `REQUIRED` or `PREFERRED` importance. |

`TargetJobTitle`, `SkillKeyword`, `SearchLocation`, `CompensationPreference`, and `ProfileCriterion` are value objects. `WorkMode`, `ContractType`, `SearchProfileStatus`, `CriterionImportance`, and `CompensationPeriod` are enums. Collections preserve user order where it improves comprehension, such as target titles and criteria.

### Why criteria are text in the MVP

Criteria need to work across sectors and countries. The MVP stores their user-written description rather than prematurely defining separate fields for every possible constraint (seniority, clearance, travel, degree, schedule, industry, and so on). A later matching design can introduce structured criterion types where evidence shows they are needed, while preserving existing descriptions.

## Business rules and invariants

- A profile belongs to exactly one user and every read or mutation is scoped to that owner.
- A profile name is required, is trimmed, has a maximum of 120 characters, and is unique per user after case-insensitive normalization.
- At least one target job title and one location are required. Each is trimmed, non-blank, and de-duplicated after normalization.
- Target titles, locations, skills, work modes, contract types, and criteria have application-level size limits to protect usability and request size. Initial proposed limits are 10 titles, 20 locations, 50 skills/keywords, 3 work modes, 8 contract types, and 30 criteria; confirm them with the UI design before implementation.
- Work modes, contract types, skills, salary preference, and criteria are optional. An empty collection means “no preference supplied”, not “exclude all offers”.
- A compensation amount is positive; where both bounds exist, minimum is not greater than maximum. Currency is a three-letter ISO 4217 code. Both bounds use the same currency and period in the MVP.
- A `REQUIRED` criterion records a user-declared non-negotiable condition. A future matching design may use it as an explicit eligibility filter only when it has reliable evidence. A `PREFERRED` criterion records a preference: it may influence relevance or explanation but must never automatically exclude an offer.
- Missing, ambiguous, or unmatched skills and experience signals lower confidence or require an explanation; they do not silently exclude an otherwise relevant offer.
- `pause()` and `reactivate()` are idempotent state changes. A paused profile remains visible and editable to its owner but is not selected by default for future recommendation or automation work.
- Deleting a profile removes only data owned by the search-profiles module. It must never cascade into future recommendation, application, or audit records. When another module needs historical context, that module must own its retained snapshot/reference and retention rule. The deletion behavior after such references exist is a future lifecycle decision, not an implicit database cascade.
- Creation and updates record creation/update timestamps and use optimistic locking to prevent silent lost updates.

## Use cases

| Use case | Input and outcome |
| --- | --- |
| Create profile | Authenticated owner submits a valid configuration. The application assigns `SearchProfileId`, sets `ACTIVE`, and returns the created profile. |
| List profiles | Owner receives only their profiles; initial order is most recently updated first. Optional status filter may include active, paused, or all. |
| Get profile | Owner reads one profile by ID. A profile owned by someone else is not disclosed. |
| Update profile | Owner replaces the editable configuration. Status remains unchanged unless the dedicated status operation is used. Optimistic-lock conflict is reported. |
| Pause profile | Owner changes `ACTIVE` to `PAUSED`; repeating the request succeeds without side effect. |
| Reactivate profile | Owner changes `PAUSED` to `ACTIVE`; repeating the request succeeds without side effect. |
| Delete profile | Owner deletes the profile, subject to the future retention decision described above. |

## Validation and error model

The API validates shape and simple fields at its boundary. The application/domain layer enforces business invariants so they apply equally to REST, tests, imports, and future clients.

| Situation | Proposed result |
| --- | --- |
| Missing/blank name, title, or location; invalid enum; malformed UUID | `400 Bad Request` with field-level problem details |
| Duplicate normalized name for the same owner | `409 Conflict` with a stable problem code |
| Invalid salary range/currency; duplicate collection entry; violated cardinality | `422 Unprocessable Content` with field-level problem details |
| Missing authentication | `401 Unauthorized` |
| Resource not found or owned by another user | `404 Not Found` to avoid ownership disclosure |
| Stale update version | `409 Conflict` with current-version guidance |

Final problem-response shape and API versioning convention remain decisions for backend bootstrap. Error messages must be actionable and must not expose data from another user.

## Proposed REST API

These endpoints are proposed for the future versioned API. They are not an OpenAPI document yet.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/v1/search-profiles` | Create a profile for the current user |
| `GET` | `/api/v1/search-profiles?status=ACTIVE` | List the current user’s profiles; `status` is optional |
| `GET` | `/api/v1/search-profiles/{profileId}` | Get one owned profile |
| `PUT` | `/api/v1/search-profiles/{profileId}` | Replace editable configuration with optimistic version |
| `PATCH` | `/api/v1/search-profiles/{profileId}/status` | Pause or reactivate a profile |
| `DELETE` | `/api/v1/search-profiles/{profileId}` | Delete one owned profile |

## Proposed PostgreSQL persistence

The schema is normalized where the profile owns repeatable values. It deliberately avoids JSONB for core searchable profile data and does not add a generic entity-attribute-value model.

```text
search_profiles
  id uuid PK
  owner_user_id uuid NOT NULL
  name varchar(120) NOT NULL
  normalized_name varchar(120) NOT NULL
  status varchar(16) NOT NULL
  version bigint NOT NULL
  created_at timestamptz NOT NULL
  updated_at timestamptz NOT NULL

search_profile_target_titles
  profile_id uuid FK -> search_profiles(id) ON DELETE CASCADE
  position smallint NOT NULL
  value varchar(160) NOT NULL
  normalized_value varchar(160) NOT NULL

search_profile_keywords
  profile_id uuid FK -> search_profiles(id) ON DELETE CASCADE
  position smallint NOT NULL
  value varchar(160) NOT NULL
  normalized_value varchar(160) NOT NULL

search_profile_locations
  profile_id uuid FK -> search_profiles(id) ON DELETE CASCADE
  position smallint NOT NULL
  label varchar(160) NOT NULL
  country_code char(2) NULL
  normalized_label varchar(160) NOT NULL

search_profile_work_modes
  profile_id uuid FK -> search_profiles(id) ON DELETE CASCADE
  work_mode varchar(16) NOT NULL

search_profile_contract_types
  profile_id uuid FK -> search_profiles(id) ON DELETE CASCADE
  contract_type varchar(20) NOT NULL

search_profile_compensation_preferences
  profile_id uuid PK/FK -> search_profiles(id) ON DELETE CASCADE
  minimum_amount numeric(12,2) NULL
  maximum_amount numeric(12,2) NULL
  currency char(3) NOT NULL
  period varchar(10) NOT NULL

search_profile_criteria
  id uuid PK
  profile_id uuid FK -> search_profiles(id) ON DELETE CASCADE
  position smallint NOT NULL
  description varchar(500) NOT NULL
  importance varchar(10) NOT NULL
```

### Integrity constraints and indexes

- Unique `(owner_user_id, normalized_name)` on `search_profiles`.
- `status`, enum columns, and `period` use `CHECK` constraints matching the application enum values.
- Collections use unique `(profile_id, position)` and normalized-value constraints where duplicate values are not meaningful, for example target titles and keywords.
- A check ensures non-negative compensation and `minimum_amount <= maximum_amount` when both values exist.
- Index `(owner_user_id, status, updated_at DESC)` supports the owner-scoped list.
- `owner_user_id` must become a foreign key to the canonical identity table when that table is introduced. Do not create a placeholder user table merely to satisfy the foreign-key shape.
- “At least one title and location” is enforced by the aggregate/application in the MVP. A cross-table database trigger would add complexity without a demonstrated need.

### Flyway migration plan

Migration names and numbers are examples; assign actual sequence numbers when the backend and identity schema exist.

1. `V1__create_identity_users.sql` or the equivalent identity migration establishes the canonical user table.
2. `V2__create_search_profiles.sql` creates the root table, owned collections, foreign keys, checks, and owner-list index in one coherent migration.
3. Later migrations add structured criteria, geocoding, retention rules, or matching projections only after their product design is approved.

No migration is created by this documentation task.

## Test plan for implementation

### Unit tests

- creating a valid profile assigns an ID, owner, `ACTIVE` status, version, and timestamps;
- rejects blank/duplicate normalized values, missing title/location, invalid cardinality, and invalid salary range;
- verifies pause/reactivate idempotency and that updates preserve status unless explicitly changed;
- verifies `PREFERRED` criteria cannot be represented as an automatic exclusion rule;
- verifies normalization and equality behavior for value objects.

### Integration tests

- Flyway applies the profile schema to an empty PostgreSQL database;
- persistence round-trip preserves ordering, enums, compensation, criteria, version, and timestamps;
- database constraints reject duplicate profile names per owner and invalid range values;
- owner-scoped repository operations cannot read or mutate another owner’s profile;
- REST tests validate requests, status transitions, error response shape, `404` privacy behavior, and optimistic-lock conflicts.

Use Testcontainers or an equivalent real PostgreSQL test environment once the backend test setup exists; do not rely only on an in-memory database for PostgreSQL constraints and migrations.

## Decisions to confirm before implementation

- Is permanent deletion acceptable before profiles are referenced by recommendations, applications, or audit records, or should deletion initially be a soft delete?
- Are the proposed limits and contract-type enum suitable for the first UI and target job markets?
- `REMOTE` is a work mode only. If a future source contains a free-text remote location, the integration module must normalize it to the work-mode field rather than storing it as a geographic location.
- What identity mechanism provides the authenticated `UserId`, and when is the `owner_user_id` foreign key available?
- Which API problem-details standard and API versioning rule will backend bootstrap adopt?
